# heer_configure() SQL Meta-Function Design

## Goal

A single SQL function that reads `heer_config`, validates the configuration, and regenerates all ID generation functions with epoch and precision baked in as constants. Eliminates the per-call config query from every ID generation.

## Problem

Currently, every call to `generate_id()`, `generate_ids()`, `generate_ranjid()`, or `generate_ranjids()` queries `heer_config` to read the epoch. This is a SELECT on every ID generation — unnecessary since the epoch never changes after deployment.

Additionally, the SQL functions need to support the new UUIDv8 precision system (2-bit precision field, 89-bit timestamp, 15-bit node). The precision must be baked into the function body so the correct bits are set without runtime lookups.

## Design

### `heer_config` Table Change

Add a `precision` column:

```sql
ALTER TABLE heer_config ADD COLUMN precision VARCHAR(2) NOT NULL DEFAULT 'ns';
```

Valid values: `us` (microseconds), `ns` (nanoseconds), `ps` (picoseconds), `fs` (femtoseconds).

### `heer_configure()` Function

**Postgres:**
```sql
CREATE OR REPLACE FUNCTION heer_configure() RETURNS void
LANGUAGE plpgsql
AS $$ ... $$;

REVOKE EXECUTE ON FUNCTION heer_configure() FROM PUBLIC;
```

**MSSQL:**
```sql
CREATE OR ALTER PROCEDURE heer_configure
AS BEGIN ... END;

REVOKE EXECUTE ON heer_configure FROM PUBLIC;
```

### Behavior

1. **Read config:**
   - `SELECT epoch, precision, ranj_epoch_offset FROM heer_config WHERE id = 1`
   - Fail if row doesn't exist

2. **Validate:**
   - Epoch is not null and not in the future
   - Precision is one of: `us`, `ns`, `ps`, `fs`
   - Compute epoch constant in the target precision unit
   - Verify the epoch constant fits in 89 bits (for RanjId) and 41 bits of milliseconds (for HeerId)
   - Verify a test HeerId and test RanjId can be generated with the baked-in constants (end-to-end smoke test)

3. **Regenerate functions:**
   - `CREATE OR REPLACE FUNCTION generate_ids(...)` with epoch as a constant (no SELECT from heer_config)
   - `CREATE OR REPLACE FUNCTION generate_ranjids(...)` with epoch and precision bits as constants
   - All wrapper functions: `generate_id()`, `generate_ranjid()`, etc.
   - Session functions remain unchanged (they don't use epoch/precision)

4. **Smoke test:**
   - Call the regenerated `generate_id(1)` and `generate_ranjid(1)` (assuming node 1 exists)
   - Verify the results are valid (non-null, positive HeerId, valid UUIDv8 RanjId)

5. **On failure — rollback:**
   - The entire operation runs inside a transaction (Postgres: implicit in plpgsql, MSSQL: explicit `BEGIN TRANSACTION`)
   - If validation fails or smoke test fails, `ROLLBACK` — the old functions remain intact
   - Raise an exception with a clear message after rollback
   - This guarantees `heer_configure()` is atomic: either everything succeeds or nothing changes

### Regenerated Function Template

The key change in the generated functions: the epoch query is replaced with a constant.

**Before (current):**
```sql
SELECT FLOOR(EXTRACT(EPOCH FROM c.epoch) * 1000)::BIGINT
INTO epoch_ms
FROM heer_config AS c
WHERE c.id = 1;
```

**After (generated by heer_configure):**
```sql
-- Epoch baked in by heer_configure() at 2026-04-05T12:00:00Z
DECLARE epoch_ms CONSTANT BIGINT := 1767225600000;
```

For RanjId, the precision bits are also baked in:
```sql
DECLARE precision_bits CONSTANT INTEGER := 1;  -- 01 = nanoseconds
DECLARE epoch_ns CONSTANT NUMERIC(30,0) := 1767225600000000000;
```

### New Bit Layout in SQL

The regenerated RanjId functions must use the new bit layout:

```
[48-bit ts_high][4-bit version=1000][12-bit ts_mid][2-bit variant=10][2-bit precision][29-bit ts_low][15-bit node_id][16-bit sequence]
```

Changes from current SQL:
- `ts_low` is 29 bits (was 30)
- Precision bits inserted between variant and ts_low
- Node ID is 15 bits (was 16)
- Version nibble is 8 (was 7) — already updated in separate commit

### Permissions

`REVOKE EXECUTE ... FROM PUBLIC` on both Postgres and MSSQL. Only the schema owner (the user who ran the migration) can call `heer_configure()`. This prevents accidental reconfiguration.

### Migration Integration

The Django migration `0001_install_heeranjid.py` should call `heer_configure()` after installing the schema and seed data:

```python
def forwards(apps, schema_editor):
    # ... install schema, functions, seed ...
    schema_editor.execute("SELECT heer_configure()")  # Postgres
    # or: schema_editor.execute("EXEC heer_configure")  # MSSQL
```

This bakes in the epoch/precision on first install. Subsequent calls to `heer_configure()` can be made manually if the config changes.

## Testing

- `heer_configure()` succeeds with valid config
- `heer_configure()` fails with missing config row
- `heer_configure()` fails with invalid precision
- `heer_configure()` fails with future epoch
- After `heer_configure()`, `generate_id()` works without `heer_config` being queried (verify by dropping heer_config after configure — IDs should still generate)
- After `heer_configure()`, `generate_ranjid()` produces UUIDv8 with correct precision bits
- Regenerated functions produce IDs with correct epoch offset
- Permission: unprivileged user cannot call `heer_configure()`

## What's NOT in scope

- Auto-calling `heer_configure()` on `heer_config` UPDATE (could be a trigger, but YAGNI)
- Migrating existing IDs when precision changes (that's the batch conversion spec)
- The `heer_configure()` function itself generating the precision-aware bit layout — that's part of the function body it writes, not a separate concern
