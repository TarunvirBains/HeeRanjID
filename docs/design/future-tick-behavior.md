# Future Tick Behavior

This note analyzes how database-backed generation behaves when a batch
allocation advances the stored generator state beyond the database wall clock.

It is a design analysis, not a committed implementation plan.

## Context

The PostgreSQL and SQL Server generators keep one state row per node. Each
state row stores the last emitted timestamp unit and sequence:

- `heer_node_state` for HeerId
- `heer_ranj_node_state` for RanjId

Generation locks the node state row, reads the last timestamp and sequence,
emits one or more IDs, then writes the final emitted timestamp and sequence
back to the state table.

This is intentional. It gives the database ownership of uniqueness and avoids
trusting application processes to coordinate ID state.

## Current Behavior

When a request needs more IDs than remain in the current timestamp unit, the
generator advances the logical timestamp and continues emitting IDs.

For HeerId:

- one timestamp unit is one millisecond
- each node has 8,192 sequence values per millisecond

For RanjId:

- one timestamp unit is the configured precision unit
- the default database SQL uses microseconds unless regenerated by
  `heer_configure()`
- each node has 65,536 sequence values per timestamp unit

This means a large batch can intentionally move `last_id_time` ahead of
`clock_timestamp()`. A later call then computes:

```text
rollback = last_id_time - now
```

If that value is positive, the current generator treats it as clock rollback
and raises an error.

That is conservative, but it conflates two different cases:

- the database clock actually moved backward
- the generator itself moved logical time forward to satisfy an earlier batch

## Why This Matters

The current behavior is safe for uniqueness. It does not create duplicate IDs.

The risk is availability and operator confusion under high-throughput or
large-batch workloads. A deployment can receive clock rollback errors even
when the database clock is healthy, simply because earlier successful
allocations consumed future logical ticks.

This is most likely when:

- most writes use one hot node
- batches are larger than one timestamp unit's remaining sequence capacity
- callers retry aggressively after rollback errors
- the system uses HeerId, where the per-node per-tick capacity is lower

The issue is less likely with RanjId because its sequence capacity is larger,
but it is still possible.

## Constraints

Any improvement should preserve these properties:

- the database remains the source of truth for ID allocation
- no duplicate IDs are possible
- IDs remain sortable by their encoded fields
- callers do not need to coordinate sequence state outside the database
- real clock rollback is still detected or bounded
- behavior is portable across PostgreSQL and SQL Server where practical

## Options

### Option A: Keep Current Error Behavior

The generator continues raising whenever `last_id_time > now`.

Advantages:

- simplest behavior
- never hides real wall-clock rollback
- no database sleeps or waits
- easiest to reason about operationally

Disadvantages:

- self-induced future ticks look like clock rollback
- high-throughput batches can cause avoidable errors
- callers need retry logic for a condition that may not be exceptional
- error messages can lead operators toward the wrong root cause

This option is safest but least ergonomic at scale.

### Option B: Continue From Logical Time

If `last_id_time > now`, the generator treats `last_id_time` as the active
logical clock and continues allocating from there.

Advantages:

- no spurious rollback errors after large batches
- preserves uniqueness
- avoids sleeps inside the database
- keeps throughput predictable under bursty workloads

Disadvantages:

- encoded timestamps can drift ahead of wall-clock time
- sustained overload on one node can keep logical time ahead indefinitely
- real clock rollback becomes harder to distinguish from generated future
  drift unless additional state or thresholds are used

This option favors availability and throughput. It needs explicit monitoring
for logical drift.

### Option C: Wait For Wall Clock To Catch Up

If `last_id_time > now`, the generator waits until the database clock reaches
the stored logical timestamp.

Advantages:

- encoded timestamps stay close to wall-clock time
- separates self-induced future ticks from hard rollback
- preserves the intuitive meaning of the timestamp field

Disadvantages:

- database functions can block while holding or waiting for generator state
- blocked calls can amplify connection pool pressure
- portable sleep behavior differs across databases
- high-throughput bursts become latency spikes

This option favors timestamp fidelity over availability.

### Option D: Cap Batch Span

The generator limits how far one request may advance logical time. Requests
that would exceed that span fail with a capacity-specific error instead of a
rollback-shaped error.

Advantages:

- prevents one request from pushing state far into the future
- makes batch sizing constraints explicit
- avoids sleeping in the database

Disadvantages:

- callers must split large batches
- does not fully solve future drift under sustained concurrency
- adds another capacity parameter that operators must understand

This option is useful as a guardrail, but not a full policy by itself.

## Recommended Direction

The best near-term improvement is a bounded version of **Option B**:

1. Classify `last_id_time > now` as logical future drift, not immediately as
   clock rollback.
2. Continue from `last_id_time` when the drift is within a configured or
   documented tolerance.
3. Raise a distinct error when drift exceeds that tolerance.
4. Use error text that distinguishes real rollback from logical future drift.

This keeps the database as the allocator, avoids sleeps, and removes the most
confusing scale failure mode. It also leaves room for stricter deployments to
set a low tolerance or disable spanning.

The tolerance should be expressed in the generator's timestamp units:

- milliseconds for HeerId
- configured precision units for RanjId

The implementation should avoid pretending the database can always prove
whether drift came from a real clock change or prior generation. Without extra
state, it can only classify the size and direction of the difference.

## Operational Guidance

For current releases:

- prefer batch generation over single-ID calls for bulk workloads
- avoid routing all high-throughput writers through one node
- use multiple registered node IDs to reduce per-row lock contention
- size batches so normal requests do not span far into future ticks
- treat rollback errors during burst generation as possible logical drift, not
  only as infrastructure clock failure
- monitor retry rates and generator errors separately from insert failures

For high-throughput deployments:

- prefer RanjId when UUID storage is acceptable
- shard hot workloads across node IDs
- keep database time synchronized with NTP in slew mode
- record `created_at` separately when exact wall-clock audit time matters

## Range Leasing Roadmap Relationship

Range leasing is a separate future design area. It would let the database
reserve larger allocation ranges atomically while still keeping the database as
the source of truth.

Future-tick behavior should be understood before range leasing is designed,
because range leasing can increase the amount of logical time reserved in one
operation. Any range-leasing design must specify:

- whether leased ranges may extend into future ticks
- how unused leased IDs are treated
- whether leases are durable, expiring, or transactional
- how logical drift is monitored and bounded
- how much generation logic remains in the database versus the caller

Until that design is complete, range leasing should remain a roadmap item, not
part of the guaranteed generation model.
