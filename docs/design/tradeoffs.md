# Design Tradeoffs

This document describes the key design decisions in HeeRanjID and the tradeoffs involved.

---

## HeerId vs RanjId

HeeRanjID provides two identifier types. Choosing between them means choosing between different capacity, storage, and compatibility constraints.

### HeerId

- 64-bit signed integer (`i64`), stored as `bigint`
- Bit allocation: 41-bit timestamp (ms), 9-bit node ID, 13-bit sequence
- Max nodes: **511**
- Max sequence per node per millisecond: **8,191**
- Max timestamp: **2,199,023,255,551 ms**
- Compact, index-efficient, no UUID tooling needed

### RanjId

- 128-bit UUID-compatible value, stored as `uuid` on PostgreSQL / `BINARY(16)` on SQL Server
- Bit allocation: 89-bit timestamp, 2-bit precision, 15-bit node ID, 16-bit sequence
- Max nodes: **32,767**
- Max sequence per node per timestamp unit: **65,535**
- Works with UUID columns, admin tooling, and APIs that expect UUID-shaped identifiers

The practical difference: HeerId is smaller and faster to index, but RanjId has nearly 64× more node capacity and 8× more sequence capacity, and is directly usable anywhere a UUID is accepted.

---

## Timestamp Precision (RanjId)

RanjId stores a timestamp in sub-millisecond precision. The precision is encoded as a 2-bit field in the UUID itself:

| Bits | Precision     | Default |
|------|---------------|---------|
| `00` | Microseconds  |         |
| `01` | Nanoseconds   | ✓       |
| `10` | Picoseconds   |         |
| `11` | Femtoseconds  |         |

The default is nanoseconds, set via the `RANJID_PRECISION` environment variable (`us`, `ns`, `ps`, `fs`). The precision is self-describing — it is encoded in each ID, so a RanjId can be decoded without knowing the generation settings.

Higher precision increases the usable timestamp range before overflow. With 89 bits of timestamp and nanosecond precision, the range is far beyond any practical deployment horizon.

HeerId stores millisecond timestamps only. No precision field is needed.

## Application-Level vs Database-Backed Generation

### Application-level generation

IDs are generated in application code using the Rust library or a language binding.

- No round-trip to the database
- Requires a unique `node_id` per running process (max 511 for HeerId, 32767 for RanjId)
- Node ID assignment is a deployment concern — two processes with the same node ID can produce colliding IDs within the same millisecond

### Database-backed generation

IDs are generated by SQL functions (`generate_id()`, `generate_ranjid()`) installed in the database.

- One DB call per ID, or one call per batch
- The database handles coordination — no per-process node ID management in application code
- Requires a live database connection at generation time
- Enables consistent ID generation across services written in different languages

Batch generation (`generate_ids(node_id, count)`, `generate_ranjids(node_id, count)`) amortizes the DB round-trip across many IDs.

### Future database allocation work

Range leasing is a possible roadmap item, not current behavior.

The idea is for the database to reserve larger ranges atomically while still
remaining the source of truth for allocation. This could reduce lock
acquisitions and round trips for high-throughput workloads, but it needs a
separate design before implementation. In particular, a range-leasing design
must define how unused leased IDs behave, how leases interact with
transactions, whether leases can expire, and how far a lease may move logical
time ahead of the database wall clock.

See [future tick behavior](./future-tick-behavior.md) for the related
tradeoffs around logical future drift.

## Conversion Constraints

HeerId → RanjId conversion is always lossless. The millisecond timestamp is scaled to the current `RANJID_PRECISION` unit, and the node ID and sequence are preserved directly.

RanjId → HeerId conversion can fail in three ways:

1. **Node ID overflow**: RanjId supports up to 32,767 nodes; HeerId supports only 511. Any RanjId with `node_id > 511` cannot be converted.

2. **Timestamp overflow**: HeerId's 41-bit millisecond timestamp has a maximum of 2,199,023,255,551 ms. A RanjId with a timestamp beyond this range cannot be converted.

3. **Sequence squash overflow**: When converting a batch, multiple RanjIds that share the same (timestamp_ms, node_id) pair after truncating to milliseconds are reassigned sequential sequence values. If more than 8,192 RanjIds map to the same millisecond slot on the same node, conversion fails.

These constraints are checked explicitly before conversion proceeds. There is no silent data loss.

## Usage patterns

Neither format is prescribed for a specific context. Some teams use HeerId for database storage and RanjId at API boundaries — this works well because the UUID string representation is stable and human-readable, while the compact integer stays close to the database. Other teams use RanjId everywhere from the start if UUID tooling compatibility matters upfront. Both are valid approaches; the important thing is that the upgrade path from HeerId to RanjId exists and is lossless if you need it later.

## UUID Compatibility

RanjId uses UUIDv8 (version bits `1000`, variant `10`). This means:

- It stores in a standard `uuid` column without schema changes
- It is accepted by UUID validators and tooling
- It is **not** UUIDv4 — parsers that validate version bits will distinguish it
- Reading an arbitrary UUIDv4 value through `RanjIdField` will raise `InvalidRanjIdVersion`

The UUID-compatible representation was chosen to allow drop-in use in existing systems without requiring new column types, while preserving the time-ordering and decodability properties that distinguish RanjId from a random UUID.
